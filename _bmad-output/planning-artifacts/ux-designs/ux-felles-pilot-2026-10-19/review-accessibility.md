# Accessibility Review — felles-pilot (WCAG 2.2 AA)

Reviewed: `DESIGN.md` (frontmatter tokens, Colors, Components), `EXPERIENCE.md` (Component Patterns, State Patterns, Interaction Primitives, Accessibility Floor, Responsive & Platform, Key Flows) and the eight mocks in `mockups/` (shared base stylesheet plus each screen's markup). Requirement context: `docs/requirements.md` §5 and E2E-10. Ratios below were recomputed from the hex values with the WCAG relative-luminance formula; the spines' own claims (16:1, 5.7:1, 5.2:1 / 4.6:1, 3.7:1, 6.4:1, ≥5:1 resource inks, ≥4.5:1 toast icons) all hold. The problems are in pairs the spine never checked and in behaviour the spine leaves open.

## Overall verdict

The contract is above average for a planning-stage spine: every token pair the designer listed passes, status is never colour-only, overlays trap and return focus, both 2-D grids have a declared linear alternative, and the mocks already carry real ARIA (grid/gridcell, switch, alertdialog, aria-live summary, hidden chart table). It is not yet AA-safe to build from: three defects would fail an audit or block keyboard users on the core booking path (focus is dropped when submit buttons are `disabled` in flight, the booking sheet has no accessible way to choose a date, and the link inside the dark toast sits at 2.70:1 with a focus ring at the same ratio), and a cluster of medium issues (colour-only active navigation, under-specified calendar keyboard model, 32 px small buttons and 28 px swatches against the spine's own 40 px floor, English Lucide ids read out as symbol names) should be settled in the spines before stories are cut. No finding is critical; 3 are high, 12 medium, 12 low.

## Findings

### High

- **[high]** Submit buttons are `disabled` while a request is in flight ("the button is disabled and shows a spinner … the form's other controls are disabled too"). Disabling the focused element throws focus to `<body>`; when the server answers with an error (login "Feil e-post eller passord.", booking 409, approve 409) the user hears the `role="alert"` but has no focus position, and a keyboard user must Tab from the top of the document to find the alert or the button again. This hits every mutation in the app and E2E-10's "skjemafeil lesbare" with keyboard. (location: EXPERIENCE.md § Component Patterns → Button; § State Patterns → Innlogging, Booking sheet; key-innlogging frame "Feil"; key-kalender frame "Booking sheet · konflikt (409)"). *WCAG:* 2.4.3, 4.1.3, 3.3.1. *Fix:* use `aria-disabled="true"` + ignore clicks during flight so focus stays on the button; on error, keep focus there (alert is announced) or move it to the inline alert (`tabindex="-1"`); on success the existing "focus returns to the trigger" rule applies. State this in the Button row.
- **[high]** The Booking sheet has no accessible date-selection component. The mock renders "Dato" as `<input type="text" value="man. 19. okt. 2026">` and the spine's only guidance is "picks ons. 21. okt." (Flow 2 step 3). A keyboard or screen-reader user has no defined way to change the date in the only flow that needs it (approval-gated equipment on another day); typing a localized string is not a specified input format. (location: EXPERIENCE.md § Key Flows Flow 2 step 3; § Component Patterns has no Date row; key-kalender frames "Booking sheet"). *WCAG:* 1.3.1, 2.1.1, 3.3.2. *Fix:* add a Date component to both spines: native `<input type="date" min max>` (30-day window) displayed with nb-NO formatting via the browser, or a 7-day chip strip (reuse Week strip semantics) plus prev/next-week buttons; specify keyboard behaviour and error text for out-of-window dates.
- **[high]** The success toast's link ("Vis i Mine bookinger") inherits `a{color:var(--color-primary)}` and sits on the `ink-primary` toast: 2.70:1 for 15 px text, and the shared `:focus-visible` ring (`#2452D9`) is also 2.70:1 against the toast. The one place the product offers a post-booking shortcut is unreadable for low-vision users and its focus is invisible. (location: DESIGN.md § Components → Toast and § Focus ring; EXPERIENCE.md § Component Patterns → Toast; base stylesheet `.toast`, `a{}`, `:focus-visible` in every mock). *WCAG:* 1.4.3, 1.4.11, 2.4.7. *Fix:* define `link-on-dark` (white, underlined, `body-strong`) and `focus-ring-on-dark` (white or `#FFFFFF`/`#7EE2A8` 2 px ring) tokens; add them to the toast spec and to the contrast table in DESIGN.md.

### Medium

- **[medium]** Toasts carrying an action auto-dismiss after 4 s. The link is only reachable by Tab (toast is `role="status"`, never focused), and "pauses on hover/focus" cannot help a keyboard user who needs several Tab presses to get there from the sheet's trigger. (location: EXPERIENCE.md § Component Patterns → Toast; § Interaction Primitives → Feedback timing). *WCAG:* 2.2.1. *Fix:* toasts without actions may stay at 4 s; toasts with a link or button persist until dismissed (or ≥ 20 s) and always have an "Lukk" button; alternatively drop the link and rely on the row already appearing in Mine bookinger.
- **[medium]** Active navigation is colour-only. Sidebar: inactive `ink-secondary` vs active `on-primary-subtle` text is 1.47:1 and the `primary-subtle` fill is 1.16:1 against white; both items use the same weight and icon. Tab bar: inactive vs active is 1.04:1 (`#596273` vs `#2452D9`) with no bar, fill or weight change. Users with colour-vision deficiency or low vision cannot see where they are; `aria-current` only helps screen-reader users. (location: DESIGN.md § Components → App shell / Sidebar "active `primary-subtle` fill", → Tab bar "active tab in `primary`"; all mocks). *WCAG:* 1.4.1, 1.4.11. *Fix:* add a non-colour cue: 3 px `primary` left bar on the active sidebar item (5.51:1 on the tint, 6.39:1 on white) and a 2 px `primary` top indicator or filled icon variant on the active tab; optionally weight 600 for the active label.
- **[medium]** The week-grid keyboard model is under-specified and the mock does not match it. The spine promises "navigable by arrow keys per 30-minute cell; Enter on an empty cell opens the sheet" but defines no accessible name for an empty cell, no `role="grid"` structure (the mock uses `role="group"` columns with absolutely positioned blocks and no cells), no behaviour for the read-only "Reservert" popover (open/close, Escape, focus return), and no content model for the "Ledige tider" alternative (what it lists, that each range is a button that opens the prefilled sheet). (location: EXPERIENCE.md § Component Patterns → Calendar (week grid); § Accessibility Floor → Calendar and picker; key-kalender desktop and mobile frames). *WCAG:* 2.1.1, 4.1.2, 1.3.1. *Fix:* specify: `role="grid"` with 7 columns × 28 rows, cell name "man. 19. okt., 10:00, ledig / opptatt / i fortiden", roving tabindex starting at the first free cell of today, Home/End/PageUp/PageDown for day/week; popover is a non-modal `role="dialog"` closed by Escape with focus return; "Ledige tider" opens a sheet listing per-day `<h3>` and buttons "10:00–11:30 (1 time 30 minutter)" that open the Booking sheet prefilled. Also give the hour gutter visible labels to the grid via `aria-rowheader` or include the time in each cell name (gutter is `aria-hidden`).
- **[medium]** Target sizes contradict the spine's own floor. The Accessibility Floor says "Controls 40 px tall; inline icon buttons 40×40 … Tap targets on mobile never fall below 40×40", but the mocks use `btn-sm` (32 px) for Godkjenn/Avslå, Avbestill/Detaljer, Rediger/Arkiver on the 375 px frames, a 32×32 close button in the Resource form sheet (`btn-icon btn-sm`), the 32 px "Vis" password toggle, and DESIGN specifies colour swatches at 28 px (mock: 36 px). Half-hour calendar cells are exactly 24 px tall (48 px hour rows), the WCAG minimum with zero margin; any 1 px gap between adjacent blocks drops them below it. All pass 2.5.8's 24 px floor, but the 32 px approve/reject buttons on a phone are the product's highest-stakes controls. (location: DESIGN.md § Layout & Spacing, § Components → Button "Small variant 32px", → Colour picker "eight 28px circles"; EXPERIENCE.md § Accessibility Floor → Targets; key-godkjenninger, key-mine-bookinger, key-ressursadministrasjon mobile frames). *WCAG:* 2.5.8. *Fix:* decide one number and make the spine and mocks agree: on < 768 px, row actions use the 40 px button; close buttons are always 40×40; swatches 40 px (or 32 px with ≥ 8 px gaps and a documented exception); hour rows 56 px so half-hour cells are 28 px.
- **[medium]** Symbol picker options are named with Lucide ids in English (`aria-label="users"`, "monitor", "door-closed", "pen-line", "headphones") and one colour is "teal". A Norwegian screen reader voice will mangle these and the user cannot map "pen-line" to anything. The spine gives colours Norwegian names ("Blå") but says nothing about symbols. (location: EXPERIENCE.md § Component Patterns → Symbol picker / Colour picker; DESIGN.md § Components → Icons list; key-ressursadministrasjon frame "Ressursskjema"). *WCAG:* 3.1.2, 2.4.6, 4.1.2. *Fix:* add a Norwegian display-name table for the ten symbols ("Personer", "Skjerm", "Dør", "Presentasjon", "Projektor", "Kamera", "Mikrofon", "Penn", "Bærbar", "Hodetelefoner") and rename "teal" to "Blågrønn"; use them as accessible names and in the "Valgt: …" text.
- **[medium]** Abbreviations leak into accessible names and live regions: "Valgt: 10:00–11:00, 1 t", "Sendt for 2 t siden", "Varighet 2 t", and date labels "man. 19. okt." in `aria-label`s and the week strip. Screen readers read "t" as the letter and "man." as "man"; sighted users get the same ambiguity with "t" (time? tirsdag?). (location: EXPERIENCE.md § Voice and Tone durations rule; § Component Patterns → Slot picker summary; key-kalender aria-labels; key-mine-bookinger "Varighet 2 t"; key-godkjenninger "Sendt for 2 t siden"). *WCAG:* 3.1.4 (AAA, but 1.3.1/4.1.2 for names), 2.4.6. *Fix:* visible text may keep "1 t 30 min"; accessible names and `aria-live` strings use full words ("1 time 30 minutter", "mandag 19. oktober"); or wrap visible abbreviations in `<abbr title>` and keep the full form in the name.
- **[medium]** Slot picker: the free slot is an operable control whose only boundary is the hairline `border` at 1.31:1, directly contradicting DESIGN's own rule "Use `border-strong` on anything the user can operate"; the "range" state (`primary-subtle`, 1.16:1 vs free slots) is distinguished only by tint and blue text; the spine says the grid has "one tab stop" yet the Floor calls the slots a "linear alternative … buttons in DOM order" (a roving-tabindex grid is not linear and they are not buttons); the base stylesheet styles `.slot[aria-pressed]` which is invalid on `gridcell`; no cell in either mock carries `tabindex="0"`, so there is no keyboard entry point; and the refusal text ("Maks 4 timer.") is placed under the grid without `aria-describedby` or a live announcement. (location: DESIGN.md § Components → Slot picker, § Do's and Don'ts; EXPERIENCE.md § Component Patterns → Slot picker; § Accessibility Floor → Calendar and picker; key-kalender sheet frames). *WCAG:* 1.4.11, 2.1.1, 4.1.2, 3.3.1. *Fix:* free slots get `border-strong` (3.73:1); range cells add a 2 px `primary` top/bottom rule or a checkmark; state the roving-tabindex rule (first free slot has `tabindex="0"`; disabled slots stay in the arrow sequence and announce "opptatt"); use `aria-selected` only; route refusals through the existing polite summary region ("Kan ikke velge 14:30: maks 4 timer.") and add a visible one-line instruction "Velg start, deretter slutt."; drop the "buttons in DOM order" sentence or make it true by offering a "Velg tid fra liste" select pair as the real linear alternative.
- **[medium]** Counters and limits disagree. EXPERIENCE says the counter "turns `danger` past the limit"; the mocks set `maxlength="200"`, so the limit can never be exceeded and the browser silently stops accepting input (no message for screen-reader users). Where a counter is live (`aria-live="polite"` on "41/200" in the Reason dialog) it announces on every keystroke. Over-limit is signalled by colour plus the digits only. (location: EXPERIENCE.md § Component Patterns → Input / Select / Textarea; key-godkjenninger Reason dialog; key-kalender "17/200"; key-ressursadministrasjon "0/200"). *WCAG:* 3.3.1, 1.4.1, 4.1.3. *Fix:* pick one: (a) no `maxlength`, counter visible, polite announcement only when crossing 180 and 200 ("20 tegn igjen", "5 tegn for mye") and an error message tied with `aria-describedby`; or (b) keep `maxlength` and announce "Maks 200 tegn nådd" once. Associate the counter to the field with `aria-describedby` in either case.
- **[medium]** Focus can be obscured by the sticky chrome. Mobile has a sticky 56 px top bar and 64 px tab bar; sheets have a sticky footer; the spine only says "content pads for the tab bar". Browsers scroll a focused element into view without accounting for sticky overlays, so Shift+Tab backwards lands focus under the top bar and the last control in a sheet body sits under the footer. (location: EXPERIENCE.md § Accessibility Floor → Focus; base stylesheet `.topbar`, `.tabbar`, `.sheet-footer`). *WCAG:* 2.4.11. *Fix:* specify `scroll-padding-top: 56px; scroll-padding-bottom: 64px` on the mobile scroll root and `scroll-padding-bottom` equal to the footer height on `.sheet-body`; include "focused element never under a sticky bar" in the S07 test bar.
- **[medium]** The "Mer" tab is an `<a href>` inside the nav but opens a sheet, and its count dot is a bare "3" (`<span class="tab-dot">3</span>`) with no accessible name, so the item reads "Mer 3". The spine's rule "Nav items are links, not buttons" is correct for the other four and wrong for this one. (location: EXPERIENCE.md § Information Architecture → Navigation; § Component Patterns → App shell; key-godkjenninger and key-ressursadministrasjon mobile frames). *WCAG:* 4.1.2, 1.3.1. *Fix:* "Mer" is a `<button aria-haspopup="dialog" aria-expanded>`; the dot carries visually hidden text "3 ventende godkjenninger"; `aria-current` is not set on a button, so mark the current page inside the Mer sheet instead.
- **[medium]** Required-field convention is undefined. The Floor says required fields are "marked in the label text ('Formål')", but "Formål" carries no marking; the Resource form marks one *optional* field with "Valgfritt" while the Booking sheet marks nothing, so a user cannot tell whether Formål is required before submitting, and nothing says `required`/`aria-required` is set. (location: EXPERIENCE.md § Accessibility Floor → Forms; key-kalender sheet; key-ressursadministrasjon sheet). *WCAG:* 3.3.2. *Fix:* adopt one convention across forms, "(valgfritt)" appended to optional labels and every other field `aria-required="true"`, state it in the Floor and list which Booking-sheet fields are required.
- **[medium]** Fill-only states and extents. Calendar block bodies are 1.12–1.16:1 against the column, so a block's end time is visible only through its text; the segmented control's selected option is a white pill on a 1.14:1 track with a faint shadow; the active nav fill is 1.16:1. Low-vision users lose duration in the calendar and the Diagram/Tabell state. (location: DESIGN.md § Components → Calendar block, → Segmented control; base stylesheet `.block`, `.segmented`). *WCAG:* 1.4.11. *Fix:* give blocks a 1 px border in the family's strong tone at 40 % alpha or a 1 px bottom rule in the edge colour; give the selected segment a `border-strong` outline or weight 600; see M2 for nav.

### Low

- **[low]** Login details: the generic error alert is not tied to the two `aria-invalid` fields (`aria-describedby` missing); the "Vis" toggle has no pressed state and its label must flip to "Skjul passord"; the 10-second throttle countdown must not update a live region every second (announce once: "Vent 10 sekunder før du prøver igjen"). The generic message is correct for 3.3.8 and `autocomplete` is set; also state explicitly that paste is allowed and no CAPTCHA/puzzle is used. (location: EXPERIENCE.md § State Patterns → Innlogging; key-innlogging error frames). *WCAG:* 3.3.1, 4.1.2, 2.2.1, 3.3.8. *Fix:* as described.
- **[low]** Inconsistent identification across mocks: `nav aria-label` is "Hovednavigasjon" in five mocks and "Hovedmeny" in two; "Logg ut" is a `<button>` on Hjem and an `<a>` elsewhere (it performs an action, so it is a button); the Godkjenninger mock renders the eyebrow as "ADMINISTRASJON" against DESIGN's no-all-caps rule (some screen readers spell capitals). (location: all mocks). *WCAG:* 3.2.4. *Fix:* one label, one element type, sentence case; the mocks' shared snippet should be the source.
- **[low]** The desktop sidebar is `position:sticky; height:100vh` with no `overflow:auto`; at 768–1023 px with browser zoom or a short window the seven items plus user block can exceed the viewport and "Logg ut" becomes unreachable without zooming out. (location: base stylesheet `.sidebar`; DESIGN.md § Layout → Between). *WCAG:* 1.4.10, 1.4.4. *Fix:* `overflow-y:auto` on the sidebar and rail; verify at 1024×600 at 150 %.
- **[low]** Text truncation and fixed heights: `.topbar .page-title` (the mobile `h1`) uses `nowrap; overflow:hidden; text-overflow:ellipsis`, so "Ressursadministrasjon" truncates under text-spacing overrides or a larger system font; calendar blocks are fixed-height `overflow:hidden`, so text-only zoom clips the time line. (location: base stylesheet `.topbar .page-title`, `.block`). *WCAG:* 1.4.12, 1.4.4. *Fix:* allow the title to wrap to two lines (top bar `min-height` 56 px); blocks under 30 minutes already show title only — state that hour-row height scales with `rem`.
- **[low]** The tab-bar label is 11 px and the Mer count dot 10 px, below DESIGN's own "nothing below 12 px" rule; both pass contrast, but 10–11 px at 375 px is hard for low-vision users before zoom. (location: DESIGN.md § Components → Tab bar; base stylesheet `.tab`, `.tab-dot`). *WCAG:* 1.4.4 (informative). *Fix:* 12 px labels; 11 px/600 for the dot with a 18 px disc.
- **[low]** `aria-label` on elements with no role (avatar `span`, `nav-count` span "3 venter", legend `div aria-label="Forklaring"`) is ignored or unreliable; the proposed pill name "Godkjenninger, 3 venter" would duplicate the link text. (location: key-dashboard, key-godkjenninger, key-kalender). *WCAG:* 4.1.2. *Fix:* visually hidden text inside the link ("3 venter"), `role="img"` + label on the avatar if it must be named, `<figcaption>`/heading for the legend.
- **[low]** The badge's "leading dot" is the same 8 px filled circle for every status, so it does not differentiate anything without colour; the text label does the work and the Utløpt dashed outline is the only shape cue. The DESIGN claim "pairs its tint with its label text and a leading dot or icon" overstates it. (location: DESIGN.md § Colors → Status, § Components → Badge). *WCAG:* 1.4.1 (passes via text). *Fix:* either drop the claim or use distinct glyphs (check, clock, x, minus) per status at 12 px.
- **[low]** Hover-only information: the Demo pill's `title="Syntetiske demodata"` is not keyboard reachable (acceptable only because the login note repeats it); the 768–1023 px icon rail "with tooltips" must show tooltips on focus as well as hover and keep them until dismissed. (location: EXPERIENCE.md § Component Patterns → Demo pill; DESIGN.md § Layout → Between). *WCAG:* 1.4.13, 2.1.1. *Fix:* rail tooltips on `:focus-visible`, dismissible with Escape; or show labels in the rail at that band.
- **[low]** Disabled-button rules conflict and under-expose reasons: Interaction Primitives say "Submit buttons stay enabled until the request starts" while the Reason dialog says "Submit disabled until valid"; the own-request Godkjenn/Avslå buttons use `aria-disabled` (good) but the reason text is not linked (`aria-describedby`), and at 50 % opacity the label is 2.32:1 (exempt, but hard to read while the user is told to read the reason nearby).
